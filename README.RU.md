# SLeeLa 3.0 — Россия (RU)

## Русское издание

SLeeLa — системный язык программирования с собственным компилятором, средой выполнения и экосистемой виртуальных машин. Проект также включает библиотеки, инструменты разработчика, документацию, процессы сборки и соглашения интеграции для поддерживаемых платформ. Технические идентификаторы, команды, пути, имена файлов, примеры кода и названия API сохраняются без изменений, чтобы инструкции можно было применять непосредственно.

**The Now. The Ingredient.** Язык программирования — это не только синтаксис. Это компилятор, среда выполнения, библиотеки, инструменты и платформенные соглашения, благодаря которым программное обеспечение можно создавать, проверять и использовать.

SLeeLa описывает направления своей работы через **Math**, **Object**, **Science** и **Reach**. Национальные интересы, относящиеся к конкретному предмету, сохраняются в явных метаданных и не исключаются этой классификацией.

## II. Возможности и последние изменения

Пакет стандартной библиотеки **Advantage** (`lib/advantage/`) моделирует оценку результата относительно модели. Его слоистая структура включает проверку, факторы, математику, добавления, вычитание, перегруппировку и итерацию. Темы охватывают двустороннюю торговую экономику, структурную физическую аналогию полей доверия (явно обозначенную как модельная аналогия), вертикальную интеграцию, оценку модулей и маршрутизируемый вывод. См. [документацию Advantage](lib/advantage/README.md).

Другие документированные возможности:

- **Управление временем циклов:** аннотации `@loopDelay` и `@loopBudget` задают паузы и временные бюджеты циклов. Они понижаются до append-only инструкции VM `OP_SLEEP` (ISA 157); эта же инструкция лежит в основе встроенной функции `sleep(ms)`. См. [спецификацию синтаксиса](SLEELA.syntax) §32 и [справочник API](api/sleela/3.0/LOOP_TIMING_API.md).
- **SleelaDoc:** команда `sleela docs` показывает документацию по темам, пакетам и классам. Команда `sleela docs --generate [dir]` создаёт локальный текстовый корпус для автономного использования. См. [библиотеку SleelaDoc](lib/sleeladoc/README.md).
- **XML DOM:** `lib/xml` предоставляет модель XML-документа с узлами элементов, текста, комментариев, CDATA и инструкций обработки, атрибутами, сериализацией и разбором. См. [документацию XML](lib/xml/README.md).
- **Целочисленные типы:** `int`, `long` и `int64` являются 64-битными знаковыми целыми числами. `int128` принимается как целочисленный тип, но пока основан на 64-битном представлении; это не следует считать полноценной 128-битной реализацией.
- **Поля `@mix`:** повторяющиеся поля экземпляра с одинаковым именем могут объединяться в индексированную последовательность, если каждое поле помечено `@mix`. См. синтаксис 2.9 в [SLEELA.syntax](SLEELA.syntax).
- **Preonems:** маркеры документа `author`, `authorial`, `material;`, `memory;`, `determine;`, `object;` и `field;` описывают статус и происхождение документа. Это декларативные маркеры, а не разрешения на выполнение кода.
- **Nordshrift:** инструмент использует рекурсивный индекс `/lib` для проверки пакетов и файлов `.sleela`.
- **Комментарии в угловых скобках:** формы `< line >` и `<< block >>` документированы как синтаксис комментариев.
- **Числовые литералы:** целые числа поддерживают шестнадцатеричную (`0x`), двоичную (`0b`) и восьмеричную (`0o`) записи с разделителем цифр `_`.
- **Metadata Class:** модули библиотеки, содержащие классы, используют шаблон метаданных для происхождения, правомерности и юрисдикционной области.
- **Text и String:** `lib/text` включает операции над текстом и строками на основе символьных ячеек, в том числе `charAt`, `substring`, `indexOf`, `reverse` и позиционное форматирование.

Описание возможности само по себе не доказывает, что она реализована и проверена для всех целей и платформ. Проверяйте актуальную реализацию и результаты тестирования.

## III. Сборка и тестирование

Требования зависят от выбранной цели сборки. Для native-реализации обычно необходимы компилятор C/C++ (например, GCC или Clang) и GNU Make. Некоторые инструменты манифестов и рабочих процессов используют Python 3. Графические компоненты Linux могут требовать пакеты разработки X11 и XRandR.

Из корневого каталога репозитория:

```sh
make
```

Сборка native-ядра и запуск набора тестов:

```sh
make -C impl all
bash ./test-suites/run-all.sh --all
```

Полезные цели Make:

```sh
make all
make clean
make help
make registry
make api-docs
```

Успешная сборка одного компонента не доказывает готовность всех библиотек или платформ к выпуску. Отчёты должны отдельно указывать тесты, которые были выполнены, пропущены или завершились ошибкой. Перед оценкой готовности к выпуску ознакомьтесь с [политикой тестирования](markdown/TESTING.md).

## IV. Установка

Для системной установки обычно используется префикс `/usr/local`:

```sh
sudo make install
```

Установка только для текущего пользователя, как правило, не требует прав администратора:

```sh
make install PREFIX="$HOME/.local"
```

Создание каталога пакета и проверка установки:

```sh
make install DESTDIR="$PWD/package-root"
make install-check
```

Следуйте инструкциям для выбранной платформы и цели. При пользовательской установке соответствующий каталог `bin` должен присутствовать в `PATH`. Не предполагайте, что одна команда установки одинаково работает в Linux, macOS и Windows: сверяйтесь с документацией платформы и доступными установочными сценариями.

## V. Язык, компилятор и среда выполнения

Нормативная спецификация языка находится в [SLEELA.syntax](SLEELA.syntax). Документация SLeeLa 3.0 описывает синтаксис, компилятор, среду выполнения, виртуальные машины и библиотеки. Версию компилятора, версию синтаксиса и версию VM/ISA необходимо рассматривать как отдельные понятия.

Типичная цепочка инструментов включает:

1. **Исходный код:** файлы `.sleela` с указанием версии языка и декларациями.
2. **Frontend:** лексический анализ, разбор, обработку символов и семантические проверки.
3. **Промежуточное представление:** структурированную форму для последующих этапов преобразования.
4. **Генерацию кода:** вывод для поддерживаемых VM- или промежуточных целей.
5. **Среду выполнения:** выполнение скомпилированного содержимого с механизмами управления памятью и потоком управления.
6. **Библиотеки и инструменты:** повторно используемые пакеты, документацию, сборку и верификацию.

Точные возможности зависят от текущей реализации. Наличие функции в спецификации не означает автоматически, что она поддерживается на каждой цели.

## VI. C, C++ и native-компиляция

Проект SLeeLa включает компоненты на C и C++ и документирует ограниченный native-путь. Маркер `@native` и команда `sleela aot` относятся к развиваемому направлению генерации native-кода. Они не являются общим разрешением на выполнение произвольного native-кода.

При взаимодействии SLeeLa с C или C++ граница интерфейса должна быть явной. Контракты ABI, владение памятью, типы данных, обработка ошибок и платформенные зависимости необходимо документировать и тестировать. Native-код следует считать отдельной границей доверия: ссылка или декларация сами по себе не дают разрешения на выполнение.

См. [native-реализацию](impl/README.md), [матрицу платформ](docs/PLATFORM-SUPPORT.md) и [стандарты сравнения](comparison/README.md).

## VII. Библиотеки и подсистемы

Репозиторий содержит обширную экосистему библиотек и инструментов. Основные разделы:

- `lib/advantage` — библиотека Advantage: определения, математика, физика, интеграция, оценка и вывод.
- `lib/xml` — модель XML-документа и сериализация.
- `lib/text` — операции над текстом и строками.
- `lib/sleeladoc` — извлечение документации и поддержка CLI.
- `lib/cpu` — модели CPU, компоненты и временные характеристики.
- `lib/xlt` — формат моделей CPU и соответствующая документация.
- `recursion/stanchion` — эталонные прототипы и примеры C/C++.
- `virtual-machine` — руководства по VM и материалы Modium.
- `api` и `docs/api` — каталог API и сгенерированный справочник.

Наличие каталога или записи в индексе не означает готовность модуля к промышленному использованию. Перед использованием изучите README модуля, тестовое покрытие, ограничения платформ и документы валидации.

## VIII. Целостность, безопасность и верификация

SLeeLa уделяет внимание прослеживаемости исходного кода, документации, сборки и результатов тестирования. Хеш-манифесты и инструменты проверки могут подтверждать соответствие файлов ожидаемому содержимому. Успешная проверка относится только к указанному объёму и моменту времени, когда она выполнялась.

Основные принципы:

- Ссылки идентифицируют ресурсы, но сами по себе не разрешают их выполнение.
- Native-интерфейсы должны быть явными и ограниченными.
- Результаты тестирования должны отдельно показывать pass, fail и skip.
- Заявления о поддержке платформ должны подтверждаться конкретными сборками и тестами.
- Сгенерированная документация должна быть связана с исходными файлами и генератором.
- Если необходимая информация об integrity отсутствует, проверки безопасности должны завершаться отказом.

См. [политику тестирования](markdown/TESTING.md), [поддержку платформ](docs/PLATFORM-SUPPORT.md) и [руководство по установке](install/README.md).

## IX. Редакторы и процесс разработки

В репозитории есть интеграции и руководства для редакторов кода. См. [интеграцию Linux-редакторов](linux-editors/README.md), где собраны ресурсы для Vim и Emacs. Перед установкой проверьте соответствие инструкций вашей операционной системе и версии редактора.

Рекомендуемый процесс внесения изменений:

1. Прочитайте индекс документации и материалы изменяемого модуля.
2. Ограничьте область изменения и объясните его назначение.
3. Добавьте позитивные и негативные тесты.
4. Запустите относящиеся к изменению тесты, а при необходимости — полный набор.
5. Запишите ОС, инструментарий, команды и фактические результаты.
6. Обновите README и API-документацию при изменении публичного поведения.
7. Не обозначайте как пройденные тесты, которые были пропущены или не запускались.
