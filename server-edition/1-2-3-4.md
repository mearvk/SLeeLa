# Server Edition 1-2-3-4-5-6 Remediation Plan

**Last reviewed:** 2026-10-26  
**Scope:** `server-edition/`  
**Purpose:** Current, actionable remediation plan for the SLeeLa Server Edition, incorporating the initial transport/security review and the subsequent hardening changes.  
**Review type:** Static source/documentation review. The CLI and default-bind changes have been committed, but a build, automated test suite, runtime test, and penetration test have not been completed in this review.  
**Overall status:** Initial hardening committed; further implementation and verification required before public production deployment.

## Current status snapshot — 2026-10-26

The command-line executable now defaults to loopback, validates port and maximum-packet-size arguments, rejects unknown options, and requires `--allow-remote` for a non-loopback bind. The transport implementation now uses strict bounded integer parsing for numeric protocol headers, an absolute deadline for each complete read operation, and a write-all loop for response statuses. The server lifecycle now uses atomic running/active-connection counters, rejects excess active clients, tracks worker threads, and joins tracked workers when the accept loop ends. This lifecycle change is still uncompiled and requires stress testing. These are source changes only: compilation and runtime tests have not yet verified them. The remote-bind gate is an exposure acknowledgement only; it does not provide TLS, peer authentication, or service authorization.

**Safe operating posture:** Keep the listener local-only unless the service is placed behind a deliberately configured, authenticated, access-controlled deployment boundary. Do not expose the current server directly to untrusted networks.

## 1. Stabilize Transport and Input Handling

**Goal:** Make packet I/O predictable under partial reads, partial writes, malformed input, and slow clients.

- [ ] Implement a write-all loop for TCP responses; handle partial sends, interruption, disconnects, and platform-specific socket errors.
- [ ] Use a monotonic deadline for each complete frame/header/payload read instead of restarting the full timeout after every partial read.
- [ ] Keep the CLI validation already added and add tests for port boundaries, invalid numeric syntax, overflow, missing values, unknown flags, and packet-size boundaries.
- [x] Validate protocol-grade, flags, stream/request/sequence numeric header values before narrowing or accepting them. **Committed; tests pending.**
- [ ] Complete semantic validation of fixed-header flags, reserved fields, header grammar, and cross-field invariants.
- [ ] Apply explicit upper bounds to header, payload, and total packet sizes; use overflow-safe arithmetic before allocation.
- [ ] Validate header names and values according to the wire protocol, including control characters and required fields.
- [ ] Ensure parser failures cannot leave partially trusted packets eligible for dispatch; make `reject_malformed` behavior effective and documented.
- [ ] Ensure response/log events reflect the actual send result; do not log a response as sent before the socket write succeeds.
- [ ] Add tests for truncated frames, oversized lengths, duplicate headers, invalid numeric fields, partial writes, peer disconnects, and slow/trickling clients.

**Exit criteria:** Partial operations are handled correctly; all untrusted lengths and numeric fields are validated; transport tests pass on each supported platform.

## 2. Correct Concurrency, Limits, and Shutdown

**Goal:** Enforce resource limits and guarantee that server-owned state remains alive while client workers use it.

- [x] Replace detached client threads with tracked joinable workers and join them after the accept loop exits. **Committed; lifecycle tests pending.**
- [x] Enforce `max_connections` as an active-connection limit separate from the `listen()` backlog. **Committed; stress tests pending.**
- [x] Make the running flag and active-connection count atomic. **Committed.**
- [ ] Define synchronization for listener descriptor access, active sockets, and concurrent `stop()`/`run()` calls.
- [ ] Stop accepting new connections, interrupt or close active work safely, join workers, then destroy packet loggers and shared state.
- [ ] Verify cross-platform behavior when closing a listening socket while another thread is blocked in `accept()`.
- [ ] Ensure Winsock startup and cleanup are paired on every success and failure path.
- [ ] Add global and per-peer rate limits with a defined time window and burst policy.
- [ ] Implement a real failure-rate policy if `max_failures_per_minute` is an enforcement control; otherwise rename/document it as a heuristic.
- [ ] Add stress tests for concurrent clients, connection floods, shutdown under load, repeated start/stop cycles, and logging during shutdown.

**Exit criteria:** No worker can outlive the server; limits are enforced; shutdown is deterministic and stress-tested.

## 3. Establish the Security Boundary

**Goal:** Prevent unauthenticated or unauthorized remote clients from reaching sensitive services.

- [ ] Keep the loopback default and explicit remote-bind gate; test both the CLI path and direct `ServerConfig` use.
- [ ] Implement TLS 1.3 with certificate validation, or document and test a supported authenticated tunnel/proxy deployment. A bind flag or firewall alone is not authentication.
- [ ] Define authenticated peer identity and service/operation authorization policies.
- [ ] Treat source IP, packet metadata, grades, classifications, and annotation fields as untrusted claims rather than identity or privileges.
- [ ] Define replay protection and request uniqueness for operations with side effects.
- [ ] Keep secrets out of logs and errors; define log permissions, rotation, retention, and disk-exhaustion behavior.
- [ ] Document firewall exposure, trusted-proxy assumptions, certificate handling, secret rotation, and production deployment requirements.
- [ ] Add negative tests for unauthenticated peers, unauthorized operations, invalid/expired credentials, replayed requests, and spoofed proxy metadata.
- [ ] State which controls are native to the server and which are deployment-provided; test the shipped path end to end.

**Exit criteria:** The trust model is implemented and documented; security tests demonstrate enforcement; remote exposure is deliberate and protected.

## 4. Complete Service Integration, Port Awareness, and Release Verification

**Goal:** Ensure the implementation matches the documented architecture and behaves consistently across supported platforms.

- [ ] Define a service-dispatch interface and route accepted packets to registered handlers.
- [ ] Inspect and test the annotation bridge API; include it in the build if intended to ship, or correct claims about the current implementation.
- [ ] Integrate port-awareness lifecycle behavior if required, including cleanup and rollback; otherwise document that firewall management is external.
- [ ] Reconcile `HTTP-GENERATIONS.md` with the implementation. Distinguish SLPK framing from native HTTP parsing and generation-specific adapters.
- [ ] Align Makefile sources and dependencies with Linux, macOS, and Windows build instructions.
- [ ] Use platform-correct socket types and startup/cleanup paths.
- [ ] Add automated build and test jobs for every platform claimed as supported.
- [ ] Run protocol, malformed-input, concurrency, lifecycle, authorization, and end-to-end service-dispatch tests.
- [ ] Update operational documentation with tested capabilities, limitations, defaults, and reproducible verification commands.

**Exit criteria:** Documentation matches tested behavior, advertised platform builds pass, and integration tests pass.

## 5. Formalize Standards, Secure Development, and Supply-Chain Controls

**Goal:** Turn security expectations into repeatable engineering checks and evidence-based release decisions.

- [ ] Maintain a threat model covering assets, trust boundaries, attackers, abuse cases, and mitigations.
- [ ] Use CWE categories to track each confirmed weakness and its remediation/test evidence.
- [ ] Map applicable requirements to OWASP ASVS as a verification checklist; record applicability and exceptions rather than claiming blanket compliance.
- [ ] Align development and release workflows with NIST SP 800-218 SSDF: review, testing, vulnerability response, and release evidence.
- [ ] Use compiler warnings and static analysis; add AddressSanitizer/UndefinedBehaviorSanitizer builds where supported and appropriate.
- [ ] Add fuzzing for packet framing, header parsing, numeric conversions, and malformed-input paths.
- [ ] Track third-party dependencies, versions, provenance, and known vulnerabilities; use dependency scanning where applicable.
- [ ] Protect release artifacts and checksums; document how source, build inputs, and artifacts are linked.
- [ ] Add a security-reporting contact and a process for triage, patching, and communicating vulnerabilities.
- [ ] Keep test evidence tied to a specific commit; do not infer compliance from a document or checklist alone.

**Exit criteria:** Security requirements are traceable to code and tests; analysis/fuzzing/dependency checks are repeatable; vulnerabilities have an ownership and response path.

## 6. Establish Protocol Conformance, Observability, and Production Operations

**Goal:** Make deployments diagnosable and ensure protocol claims, operational behavior, and release evidence are verifiable.

- [ ] Define a versioned protocol specification with required/optional fields, canonical numeric ranges, framing limits, error codes, compatibility rules, and unknown-field behavior.
- [ ] Add golden test vectors and independent client/server interoperability tests for every supported protocol version.
- [ ] Define compatibility and deprecation rules; test backward/forward compatibility instead of relying on generation labels alone.
- [ ] Standardize structured log event names, timestamps, correlation IDs, and result fields while redacting secrets and sensitive payload data.
- [ ] Add operational metrics for active connections, rejected frames, timeout counts, rate-limit actions, handler latency, and internal errors; avoid high-cardinality labels and sensitive data.
- [ ] Add health/readiness behavior that does not expose sensitive configuration or treat a listening socket as proof that application services are healthy.
- [ ] Define graceful shutdown, restart behavior, log rotation, retention, disk-full handling, and resource limits in deployment documentation.
- [ ] Document service ownership, authorization policy, firewall/network requirements, backup/recovery needs for any durable state, and incident response steps.
- [ ] Add deployment smoke tests and a release checklist that records commit, compiler/toolchain, platform, test results, known issues, and rollback instructions.
- [ ] Review public claims and examples for accuracy; label unimplemented adapters, features, and standards mappings as planned rather than supported.

**Exit criteria:** Protocol behavior is testable and versioned; operational signals and runbooks exist; production releases have reproducible evidence and rollback guidance.
