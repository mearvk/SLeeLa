# SLeeLa Performance Assessment — Basic Data Types and RAM Access

## 1. Purpose

This assessment defines a reproducible comparison of computation speed and memory-access performance across:

1. The Basic SLeeLa Native VM in `impl/core`.
2. All ten Standard/think-tank VM generations, `idea-vm-001` through `idea-vm-010`.
3. All eleven runnable Premium VMs, SLVM/1 through SLVM/11.
4. Native C11 and C++17 implementations.
5. Java 21 or later on the JVM.

The purpose is to measure real execution, not infer speed from version number, feature count, source-code size, or architectural description. No performance values or rankings are asserted in this protocol. Results must be generated by the benchmark runners and retained with their environment metadata before conclusions are drawn.

## 2. Architecture and fair-comparison rules

### 2.1 Basic Native VM

The baseline is the Native VM implemented by `impl/core`, invoked through the repository's normal SLeeLa compiler/runtime path. It is the default SLeeLa execution engine.

### 2.2 Standard VMs: generations 1–10

The Standard progression is:

| Generation | Registry identity | Documented addition |
|---:|---|---|
| 1 | `idea-vm-001` | Ground-floor configuration, report, status |
| 2 | `idea-vm-002` | Memory hardening |
| 3 | `idea-vm-003` | Typed results |
| 4 | `idea-vm-004` | Telemetry |
| 5 | `idea-vm-005` | Garbage-collection quality |
| 6 | `idea-vm-006` | Dispatch profiler |
| 7 | `idea-vm-007` | Capability enforcement |
| 8 | `idea-vm-008` | Platform parity |
| 9 | `idea-vm-009` | Audit trail |
| 10 | `idea-vm-010` | Consolidated runtime |

**Execution qualification:** the repository's VM user guide currently identifies Standard generations 1–10 as a layered think-tank progression and explicitly says they are not yet bootable through the Premium-style `sleela vm run` command. They must therefore not be represented as ten independently executing instruction engines in this report.

The Standard generations remain in scope. Their assessment is divided into:

- **Layer/control-plane cost:** measure the initialization, configuration, memory checks, typed-result handling, telemetry, GC observation, profiling, capability checks, platform checks, audit writes, and consolidated-runtime operations that are actually exposed by their source APIs.
- **Incremental cost:** where a generation adds a measurable operation, compare that operation with the immediately preceding generation and with the uninstrumented Core baseline.
- **Whole-program execution:** mark as **NOT RUN / NOT BOOTABLE** until the repository supplies a supported executable path for that Standard generation. Do not substitute the Native VM and label it as a Standard VM result.

If a Standard layer has no independently callable operation or faithful native harness, record it as unavailable rather than inventing a measurement.

### 2.3 Premium VMs: generations 1–11

The Premium SLVM runners each link the shared Core archive and perform their own grade-specific admission/validation before running a compiled SLeeLa artifact. Their distinguishing feature validators are part of the measured architecture.

For every Premium generation, report two distinct timings:

1. **Steady-state workload:** elapsed time to execute the same precompiled workload after the runner has started and admitted the VM.
2. **Cold invocation:** process start, admission, artifact load, execution, and shutdown as one end-to-end interval.

The steady-state result is the primary computation comparison. Cold invocation is a separate operational metric. Do not attribute a difference in admission time to arithmetic throughput.

### 2.4 Native language comparators

| Comparator | Required language/runtime |
|---|---|
| C | C11, optimized native build |
| C++ | C++17, optimized native build |
| Java | Java 21+; record exact JDK vendor and version |

C and C++ are native baselines, not VM implementations. Java results include JVM/JIT behavior and must use warm-up and steady-state measurement. These results are comparative reference points, not proof that the languages have identical semantics or implementation strategies.

## 3. Basic data-type computation suite

Each implementation must run the same defined inputs, iteration counts, dependency patterns, and observable result checks. Inputs and outputs are fixed and included in the result record. Use integer-safe workloads with defined overflow behavior; do not rely on signed overflow in C or C++.

| ID | Data type / operation | Primary measurement |
|---|---|---|
| DT-01 | Boolean operations and conditional selection | operations/second |
| DT-02 | 8/16/32-bit integer arithmetic | operations/second |
| DT-03 | 64-bit signed and unsigned integer arithmetic | operations/second |
| DT-04 | 128-bit integer arithmetic where natively supported | operations/second; support recorded |
| DT-05 | Single-precision floating-point arithmetic | operations/second |
| DT-06 | Double-precision floating-point arithmetic | operations/second |
| DT-07 | Integer comparisons, branches, and loops | iterations/second |
| DT-08 | Integer division and remainder | operations/second |
| DT-09 | Function calls and return-value handling | calls/second |
| DT-10 | Mixed-type arithmetic/conversion where supported | operations/second |
| DT-11 | Array element reads and writes | elements/second |
| DT-12 | String construction, comparison, and traversal | operations/second or bytes/second, with exact semantics stated |

The suite must distinguish arithmetic throughput from dispatch overhead. Include both dependency-chain tests (each result depends on the previous result) and independent-operation batches (multiple independent values per iteration). This helps reveal latency versus throughput and reduces the risk that compiler/JIT optimization removes the work.

For floating point, report precision mode and validation tolerance. For 128-bit integers, record whether the implementation uses a native 128-bit representation, a library representation, or a narrower fallback. Do not compare unlike implementations without disclosing that distinction.

## 4. RAM and memory-access suite

RAM testing is separated into latency, bandwidth, cache behavior, and allocation/reclamation. A single generic “RAM speed” number is insufficient.

| ID | Test | Measurement |
|---|---|---|
| MEM-01 | Sequential read | GiB/s |
| MEM-02 | Sequential write | GiB/s |
| MEM-03 | Read-modify-write stream | GiB/s and operations/second |
| MEM-04 | Sequential copy | GiB/s |
| MEM-05 | Random read, fixed working set | ns/access and accesses/second |
| MEM-06 | Dependent pointer chase over randomized permutation | ns/load; latency |
| MEM-07 | Random write | ns/store and operations/second |
| MEM-08 | Strided access | ns/access and effective GiB/s |
| MEM-09 | Working-set sweep | latency/bandwidth by allocation size |
| MEM-10 | Allocation and release | allocations/second and ns/allocation |
| MEM-11 | Array growth / append | ns/element and total throughput |
| MEM-12 | GC allocation/reclamation pressure, where applicable | allocation rate, pause time, reclaimed bytes |

### 4.1 Working-set sizes

Use a documented geometric size sweep that includes small cache-resident sets and sets larger than the last-level cache and physical memory only where safely available. Suggested default sizes are 4 KiB, 32 KiB, 256 KiB, 2 MiB, 16 MiB, 64 MiB, and 256 MiB. The runner must detect available memory and cap the largest allocation conservatively; it must never intentionally exhaust the host.

Record actual allocation size, page size when available, and whether the test data fits in the relevant cache. Do not label a size “L1”, “L2”, “L3”, or “RAM” unless the host's cache topology supports that label.

### 4.2 Latency versus bandwidth

- Sequential streaming primarily measures bandwidth and prefetch effectiveness.
- Random independent accesses measure a mix of memory-level parallelism and latency.
- Dependent pointer chasing suppresses parallel look-ahead and is the primary memory-latency probe.
- Strided tests reveal cache-line utilization and access-pattern sensitivity.

Report these as separate metrics. Never convert a bandwidth result into a latency claim.

## 6. Execution protocol

1. Record repository commit SHA, branch, dirty-tree state, compiler versions, JDK vendor/version, OS/kernel, CPU model, logical/physical core counts, RAM capacity, memory speed if available, cache sizes, and power mode.
2. Use one physical host for a direct within-host comparison. Run a separate complete matrix for each additional OS/host; never compare numbers from unlike hardware as though the runtime caused the difference.
3. Build native C and C++ with documented release optimization and warnings. Record the exact compiler command and flags. Build SLeeLa Core and every Premium runner from the same repository commit and compatible release configuration.
4. Compile SLeeLa source once per workload to the same artifact format and use that artifact for the Basic VM and every Premium runner. Record compiler version, artifact hash, and compile time separately. Compilation time is not VM execution time.
5. Compile Java comparators once. Warm up the JVM until the measured workload stabilizes or a declared warm-up ceiling is reached. Record warm-up iterations and JVM flags. Report cold JVM startup separately.
6. Perform at least five measured repetitions after warm-up; use a longer run duration for short operations. Report median, minimum, maximum, and p95 where sample count permits. Include dispersion (standard deviation or median absolute deviation).
7. Alternate or randomize target execution order to reduce thermal, frequency, and background-load bias. Record CPU governor/power plan and avoid concurrent benchmark workloads.
8. Validate the final result/checksum of every workload. A run with a wrong result, missing workload, runtime error, or unsupported operation is not a performance result.
9. Keep process startup, VM admission, artifact loading, steady-state execution, and shutdown as separate phases wherever instrumentation allows.
10. Repeat the full suite on each target OS before making cross-platform claims. The initial reference run may use Ubuntu, but it must be labeled Linux-only until macOS and Windows runs complete.

## 7. Measurement and reporting rules

- Primary throughput unit: operations/second or iterations/second.
- Memory bandwidth: decimal bytes/second and GiB/s, with the conversion stated.
- Memory latency: nanoseconds/access.
- Time: monotonic high-resolution clock; use the same measurement boundary within each language/runtime.
- Normalize only as a secondary view. Preserve raw elapsed time, operation count, and bytes transferred.
- Report ratios against C11, C++17, Java 21+, and the Basic Native VM separately. Do not combine all comparators into one synthetic score.
- Provide both absolute values and relative ratios. A faster/slower percentage must identify its denominator.
- Flag outliers and disclose exclusions; never silently discard inconvenient runs.
- No ranking is valid unless the same workload, input, hardware, and measurement boundary were used.

### 7.1 Compiler/JIT and optimization controls

C/C++ builds must prevent dead-code elimination by validating a checksum observable outside the timed loop. Avoid undefined behavior and ensure allocation alignment is comparable. Record optimization flags, LTO state, target architecture flags, and allocator.

Java must record JDK and VM flags, warm-up policy, garbage collector, heap bounds, and whether compilation reached steady state. Report GC activity and pauses for memory-pressure workloads. A Java result before JIT warm-up must not be compared with a steady-state native result without an explicit cold-start label.

SLeeLa must use the same compiler/artifact and runtime build for the Basic and Premium comparisons. Do not include compilation in steady-state execution time. Record Core build flags and Premium admission checks.

## 8. Standard VM layer accounting

For each Standard generation, record the following where its source exposes a callable operation:

- initialization/configuration cost;
- per-operation cost of the generation's added layer;
- memory footprint of the layer's state;
- telemetry/profiling/audit event cost where applicable;
- GC observation/collection coordination cost where applicable;
- capability-check cost where applicable;
- consolidated-runtime polling and shutdown cost.

Use a paired baseline: run the same underlying operation with the layer disabled/absent and enabled/present, with identical inputs. Report incremental time and memory, not only total time. If a layer changes the semantics or amount of work, the pair is not directly comparable and must be described.

Until a supported executable Standard-VM route exists, report the whole-program execution field as **NOT RUN — Standard generation not bootable through the documented runner**. Do not claim that a source-level manifest or a selection record is an executing VM.

## 10. CI and execution policy

Correctness and performance must be separate CI concerns.

- CI should compile and validate the benchmark programs and verify result checksums.
- Timing runs should be manually dispatched or run on controlled, stable benchmark hosts; ordinary shared GitHub-hosted runners are too variable for release-grade speed rankings.
- CI may retain timing observations as informational data, but noisy timing variance must not fail correctness CI.
- A benchmark report is **PASS** only when all required workloads for its declared scope completed, their results validated, and raw results plus environment metadata were retained.
- A partially completed target matrix is **PARTIAL**, not PASS.
- A design-only document, unexecuted runner, or CI workflow that merely compiles tests is **NOT A MEASUREMENT**.
