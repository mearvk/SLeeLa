SLXltBuildResult #sleela 2.5 (lib/xlt/SLXltBuildResult.sleela)

SLXltBuildResult class

Defines SLXltBuildResult — the outcome of compiling an .xlt CPU-model sheet. Per the format's contract, compilation yields exactly one of two things: (a) SUCCESS: the model was built, with a list of what was built (the CPU SKU and each part that resolved and was installed), or (b) a CONGRUENCE report: an ordered list of reasons the model could NOT be built — a missing part (a declared ref resolved to nothing) or a part that is "not agreeable to design" (resolves, but does not agree with another declared part, e.g. memory channels exceeding the board). The result is deliberately like a diagnostics bag: structured, ordered, and human-readable, so the author sees precisely why integrity failed, in the document order the parts were declared. Family: xlt. Produced by SLXltCompiler. Mirrors the role of Nordshrift's diagnostics + component manifest for the SST path.

SLXltProducerRegistry #sleela 2.5 (lib/xlt/SLXltProducerRegistry.sleela)

SLXltProducerRegistry class

Defines SLXltProducerRegistry — the explicit registry of part producers the XLT compiler resolves declared refs against. Instead of the compiler hardcoding "is this a known ref" tables inline, each recognizable part ref (CPU SKU, memory preset, board, cadence, storage, bus) is REGISTERED here under its slot, and the compiler asks the registry whether a ref is known and (for memory/board) what channel count it implies for the agreement check. A new part becomes recognizable by registering it, not by editing the compiler — the open/closed seam the SST symbol tables have. A registered entry carries: the slot it belongs to, the ref string, and an integer attribute (memory channel count, or board routed channels; 0/1 otherwise). Registration order does not matter; lookup is by (slot, ref). Family: xlt. Consulted by SLXltCompiler; mirrors the resolution role of lib/sst/SSTSymbolTable for the CPU-model format.

SLXltRefBank #sleela 2.5 (lib/xlt/SLXltRefBank.sleela)

SLXltRefBank class

Defines SLXltRefBank — a small fixed-capacity bank of String values indexed by integer position, used by SLXltProducerRegistry to hold the ref string of each registered producer (SLRAM stores words, not strings, so the registry pages its integer attributes into SLRAM and its ref strings into this bank at the same index). The surface language has no arrays, so the bank is a bounded set of explicit slots selected by index, the same idiom SLVMClass uses for its f0..f7 / m0..m7 members. Family: xlt. Internal helper for SLXltProducerRegistry.
