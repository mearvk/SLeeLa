# Server Edition 1-2-3-4 Remediation Plan

**Last reviewed:** 2026-10-26  
**Scope:** `server-edition/`  
**Purpose:** Current, actionable remediation plan for the SLeeLa Server Edition based on a review of the `master` branch source.  
**Review type:** Static source/documentation review only. No build, automated test suite, runtime test, or penetration test was executed as part of this review.  
**Overall status:** Remediation required before public production deployment.

## Current status snapshot — 2026-10-26

The current source still exhibits the principal transport, lifecycle, and security issues below. Treat this as the baseline for implementation tracking, not as evidence that any item has been fixed.

| Area | Current observation | Priority |
|---|---|---|
| Network exposure | `ServerConfig` defaults to `0.0.0.0:19866`; the README's example also explicitly binds to all interfaces. | Critical |
| Authentication and transport security | The inspected server path does not implement authenticated peer identity or TLS. | Critical |
| Worker lifecycle | Client threads are detached and access server-owned state; orderly worker joining is not implemented. | Critical |
| Concurrency state | `running_` is read and written across threads without being atomic or consistently protected by the same lock. | High |
| Connection limits | `max_connections` is passed to `listen()` as a backlog; it does not cap active client workers. | High |
| Socket handling | Responses use a single `send()`; partial writes are not retried. Read timeouts restart for each partial read. | High |
| Rate limiting | The inspected rate check is per connection and uses an elapsed-time integer average, not a global/per-peer windowed limiter. | High |
| Input validation | CLI port conversion narrows to 16 bits without an explicit range check; header numeric values are cast without field-specific range validation. | High |
| Service dispatch | The inspected client path acknowledges accepted packets but does not dispatch them to application service handlers. | High |
| Build/documentation alignment | README describes generation adapters and an annotation bridge; the inspected Makefile does not compile `annotation_language_bridge.cpp`. | High |
| Platform support | Socket descriptors are stored as `int`; Windows `SOCKET` handling and the documented Windows build path need validation. | High |
| Firewall lifecycle | Documentation defines a port-awareness contract, but the inspected socket server does not itself apply firewall rules. | Medium |

**Safe operating posture until remediation:** Keep the listener bound to loopback or behind a properly configured, authenticated, access-controlled deployment boundary. Do not expose this implementation directly to untrusted networks. A firewall or reverse proxy is not a substitute for application-level identity and authorization.

## 1. Stabilize Transport and Input Handling

**Goal:** Make packet I/O predictable under partial reads, partial writes, malformed input, and slow clients.

- [ ] Implement a write-all loop for TCP responses; handle partial sends, interruption, disconnects, and platform-specific socket errors.
- [ ] Use a monotonic deadline for each complete frame/header/payload read instead of restarting the full timeout after every partial read.
- [ ] Validate command-line values before narrowing or conversion: port range (1–65535, unless port 0 is intentionally supported), numeric syntax, overflow, and missing option values. Reject unknown options and provide clear `--help` output.
- [ ] Validate protocol-grade values, flags, stream/request/sequence fields, and all numeric header values before casting or accepting them.
- [ ] Apply explicit upper bounds to every accepted header, payload, and total packet; use overflow-safe arithmetic before allocation.
- [ ] Validate header names and values according to the wire protocol, including control characters and required fields.
- [ ] Decide and document whether malformed packets are rejected or logged-and-continued; ensure the `reject_malformed` configuration is actually honored.
- [ ] Ensure response/log events reflect the actual send result; do not log a response as sent before the socket write succeeds.
- [ ] Add tests for truncated frames, oversized lengths, duplicate headers, invalid numeric fields, partial writes, peer disconnects, and slow/trickling clients.

**Exit criteria:** I/O handles partial operations correctly; untrusted lengths and numeric fields are validated; transport tests pass on each supported platform.

## 2. Correct Concurrency, Limits, and Shutdown

**Goal:** Enforce resource limits and guarantee that server-owned state remains alive while client workers use it.

- [ ] Replace detached client threads with a managed worker pool or tracked joinable workers.
- [ ] Enforce `max_connections` as an actual active-connection limit. The `listen()` backlog alone is not a connection limit.
- [ ] Make server lifecycle state thread-safe (for example, an atomic stop flag plus clearly defined synchronization for the listener and active sockets).
- [ ] Define a shutdown sequence that stops accepting connections, interrupts or closes active sockets as appropriate, joins workers, then destroys packet loggers and other shared state.
- [ ] Verify cross-platform behavior when closing a listening socket while another thread is blocked in `accept()`.
- [ ] Ensure Winsock startup and cleanup are paired on every success and failure path.
- [ ] Add global and per-peer rate limits with a defined time window and burst policy; avoid integer-average checks that allow bursts or easy multi-connection evasion.
- [ ] Implement a real failure-rate policy if `max_failures_per_minute` is intended as an enforcement control; otherwise rename/document it as a heuristic.
- [ ] Add stress tests for concurrent clients, connection floods, shutdown under load, repeated start/stop cycles, and log activity during shutdown.

**Exit criteria:** No worker can outlive the server; limits are enforced; shutdown is deterministic and stress-tested.

## 3. Establish the Security Boundary

**Goal:** Prevent unauthenticated or unauthorized remote clients from reaching sensitive services.

- [ ] Change the default bind address to loopback or another safe local-only setting; require explicit configuration to expose the service publicly.
- [ ] Define a supported protected-transport deployment. Prefer TLS with certificate validation, or a clearly documented authenticated tunnel when TLS is terminated by a trusted front end.
- [ ] Define peer identity and authentication requirements; do not treat a successful TCP connection, source IP, or application metadata as authenticated identity.
- [ ] Add service- and operation-level authorization tied to the authenticated identity.
- [ ] Define replay protection and request uniqueness where operations can have side effects; document sequence persistence and restart behavior.
- [ ] Keep secrets out of logs and errors; review log fields for personal, credential, and payload leakage.
- [ ] Document firewall exposure, trusted proxy assumptions, certificate handling, secret rotation, and production deployment requirements.
- [ ] Add negative tests for unauthenticated clients, unauthorized services/operations, invalid or expired credentials, replayed requests, and unexpected proxy headers.
- [ ] Document which controls are provided by the server and which must be supplied by a deployment front end; test the actual shipped path end to end.

**Exit criteria:** The trust model is documented and implemented, public exposure is deliberate, and security tests demonstrate enforcement. Do not claim TLS or authentication support until it is present and tested in the shipped path.

## 4. Complete Service Integration, Port Awareness, and Release Verification

**Goal:** Ensure the implementation matches the documented architecture and behaves consistently across supported platforms.

- [ ] Define a service-dispatch interface and route accepted packets to registered handlers; an acknowledgement alone is not application-service execution.
- [ ] Inspect and test the annotation bridge API and implementation. Add its source and dependencies to the build if it is intended to ship, or correct the documentation to describe the actual current scope.
- [ ] Integrate the port-awareness lifecycle module if required: define ownership and cleanup for firewall rules, failure rollback, and least-privilege behavior. Otherwise, explicitly document that firewall management is external to the server.
- [ ] Reconcile `HTTP-GENERATIONS.md` and related documentation with the actual protocol implementation. Distinguish SLPK framing from native HTTP parsing and from any generation-specific adapters.
- [ ] Align Makefile sources and link dependencies with the documented Linux, macOS, and Windows build instructions. Ensure the Windows instructions include every required source and library.
- [ ] Use platform-correct socket types and startup/cleanup paths; verify Winsock and POSIX implementations separately.
- [ ] Add automated build and test jobs for Linux, macOS, and Windows where those platforms are claimed as supported.
- [ ] Run protocol conformance, malformed-input, concurrency, lifecycle, authorization, and end-to-end service-dispatch tests.
- [ ] Update README and production documentation with tested capabilities, limitations, configuration defaults, and exact verification commands.
- [ ] Record test output and commit/PR references for each completed item; do not mark work verified based on documentation changes alone.

**Exit criteria:** Documented features correspond to working code, supported-platform builds pass, and integration/end-to-end tests pass.
