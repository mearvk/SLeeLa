# Server Edition 1-2-3-4 Remediation Plan

**Scope:** `server-edition/`  
**Purpose:** Track the four implementation stages needed to address the findings from the server-edition source review.  
**Status:** Planning document; items are not considered complete until implemented and verified by tests.

This plan reflects a static source review, not a runtime security assessment. Do not treat the server as production-ready until the relevant controls and tests have passed.

## 1. Stabilize Transport and Input Handling

**Goal:** Make packet I/O predictable under partial reads, partial writes, malformed input, and slow clients.

- [ ] Implement a write-all loop for TCP responses; handle partial sends, interruption, disconnects, and platform-specific socket errors.
- [ ] Use a monotonic deadline for each complete frame/header/payload read instead of restarting the full timeout after every partial read.
- [ ] Validate command-line values before narrowing or conversion: port range, numeric syntax, zero/overflow cases, and unknown options. Provide `--help`.
- [ ] Validate protocol-grade values and all length fields before casting or allocating memory.
- [ ] Apply explicit upper bounds to every accepted header, payload, and total packet; reject malformed frames consistently.
- [ ] Decide and document whether malformed packets are rejected or logged-and-continued; ensure the `reject_malformed` configuration is actually honored.
- [ ] Add tests for truncated frames, oversized lengths, duplicate headers, invalid numeric fields, partial writes, peer disconnects, and slow/trickling clients.

**Exit criteria:** I/O handles partial operations correctly; all untrusted lengths and numeric fields are validated; transport tests pass.

## 2. Correct Concurrency, Limits, and Shutdown

**Goal:** Enforce resource limits and guarantee that server-owned state remains alive while client workers use it.

- [ ] Replace detached client threads with a managed worker pool or tracked joinable workers.
- [ ] Enforce `max_connections` as an actual active-connection limit. The `listen()` backlog alone is not a connection limit.
- [ ] Make server lifecycle state thread-safe (for example, an atomic stop flag or correctly synchronized state).
- [ ] Define a shutdown sequence that stops accepting connections, interrupts or closes active sockets as appropriate, joins workers, then destroys loggers and other shared state.
- [ ] Verify cross-platform behavior when closing a listening socket while another thread is blocked in `accept()`.
- [ ] Add global and per-peer rate limits with a defined time window and burst policy; avoid integer-average checks that allow bursts or easy multi-connection evasion.
- [ ] Implement a real failure-rate policy if `max_failures_per_minute` is intended to be an enforcement control; otherwise rename/document it as a heuristic.
- [ ] Add stress tests for concurrent clients, connection floods, shutdown under load, and repeated start/stop cycles.

**Exit criteria:** No detached worker can outlive the server; limits are enforced; shutdown is deterministic and stress-tested.

## 3. Establish the Security Boundary

**Goal:** Prevent unauthenticated or unauthorized remote clients from reaching sensitive services.

- [ ] Change the default bind address to loopback or another safe local-only setting; require explicit configuration to expose the service publicly.
- [ ] Define a supported protected-transport deployment. Prefer TLS with certificate validation, or a clearly documented authenticated tunnel when TLS is terminated by a trusted front end.
- [ ] Define peer identity and authentication requirements; do not treat a successful TCP connection as an authenticated identity.
- [ ] Add service- and operation-level authorization tied to the authenticated identity.
- [ ] Define replay protection and request uniqueness where operations can have side effects.
- [ ] Keep secrets out of logs and errors; review log fields for personal, credential, and payload leakage.
- [ ] Document firewall exposure, trusted proxy assumptions, certificate handling, and production deployment requirements.
- [ ] Add negative tests for unauthenticated clients, unauthorized services/operations, expired or invalid credentials, replayed requests, and unexpected proxy headers.

**Exit criteria:** The trust model is documented and implemented, public exposure is deliberate, and security tests demonstrate enforcement. Do not claim TLS or authentication support until it is present and tested in the shipped path.

## 4. Complete Service Integration, Port Awareness, and Release Verification

**Goal:** Ensure the implementation matches the documented architecture and behaves consistently across supported platforms.

- [ ] Define a service-dispatch interface and route accepted packets to registered handlers; an acknowledgement alone is not application-service execution.
- [ ] Wire the annotation-language bridge into the build only after its API and implementation are verified, or correct the documentation to describe the actual current scope.
- [ ] Integrate the port-awareness lifecycle module if required: define ownership and cleanup for firewall rules, failure rollback, and least-privilege behavior. Otherwise, explicitly document that the server does not manage firewall rules.
- [ ] Reconcile `HTTP-GENERATIONS.md` and related documentation with the actual protocol implementation. Distinguish SLPK framing from native HTTP parsing and from any generation-specific adapters.
- [ ] Align Makefile sources and link dependencies with the documented Linux, macOS, and Windows build instructions.
- [ ] Fix platform-specific socket types and startup/cleanup paths; verify Winsock and POSIX implementations separately.
- [ ] Add automated build and test jobs for Linux, macOS, and Windows where those platforms are claimed as supported.
- [ ] Run protocol conformance, malformed-input, concurrency, lifecycle, authorization, and end-to-end service-dispatch tests.
- [ ] Update README and production documentation with tested capabilities, limitations, configuration defaults, and exact verification commands.

**Exit criteria:** Documented features correspond to working code, supported-platform builds pass, and integration/end-to-end tests pass.

| Field | Record |

Do not mark an item complete based solely on documentation edits. Security-sensitive claims require implementation evidence and tests.
