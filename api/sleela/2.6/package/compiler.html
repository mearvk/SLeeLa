SLCompileChoice #sleela 2.5 (lib/compiler/SLCompileChoice.sleela)

SLCompileChoice class

Defines SLCompileChoice, the compiler's decision about which source form to compile, making .sldocument a selectable compile choice. A developer tells the compiler "compile this as a program" or "compile this as an ordered document". SLCompileChoice records that selection, resolves it from a file name when not stated explicitly, and routes to the right front end: - a .sleela program compiles through the ordinary SLeeLa Compiler path; - a .sldocument compiles through the document-aware path (which still uses the SLeeLa Compiler for the step methods and any companion .sleela source). The choice is explicit and fail-closed: an unknown form is not guessed; it is surfaced as a diagnostic. Family: compiler. Native VM/OS work crosses an explicit bridge.

SLLanguageCompiler #sleela 2.5 (lib/compiler/SLLanguageCompiler.sleela)

SLLanguageCompiler class

Defines SLLanguageCompiler, the language-neutral base contract a developer extends to build a compiler for any publicly known programming language (C, C++, Java, Python, JavaScript, Rust, Go, ...). This is the heart of the modular compiler framework. A new language front end is created by subclassing SLLanguageCompiler and overriding the pipeline phases it provides. Every front end lowers its own language toward the common SLeeLa IR and, from there, a VM-ready artifact — so the authoritative path stays: <language> source -> front end -> SLeeLa IR -> VM lowering -> SLVM/SLJVM The framework does not create a parallel language and does not grant itself VM, capability, security, resolver, memory, or certificate authority. A produced artifact is only ever executed later, across an explicit SLeeLa VM/OS and security boundary. Compilation is not execution. Family: compiler. Native VM/OS work crosses an explicit bridge.
