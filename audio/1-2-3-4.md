### Final C correction

On 2026-09-28, the final review found that the C implementation did not retain the loaded WAV byte count in its `bytes[i]` bookkeeping before its second parsing pass. That could cause the second pass to treat the buffer as empty.

The correction:

- records the actual input size;
- preserves the second-pass data-chunk scan;
- adds audio-length overflow protection;
- adds output-buffer size protection.

## 3. Native/Java Contract Review

**Date:** 2026-09-28

The final review identified one contract item that must remain explicit.

The current Java adapter invokes the native executable as:

```
executable OUTPUT SAMPLE_RATE INPUT...
```

The Java `Configuration` model also contains:

- input start time;
- input gain;
- bass;
- mid;
- treble;
- master gain;
- pan;
- left gain;
- right gain.

The current process invocation does not transmit all of those fields to the native executable.

Therefore:

- the native C/C++ APIs remain the authoritative parameterized mixer interfaces;
- the Java process adapter must not be described as transmitting the complete `Configuration` until its process protocol is expanded;
- future protocol work should define an unambiguous argument/configuration representation for offsets, gains, EQ, and channel controls.

This distinction is intentional. It prevents the Java API from claiming a capability that the current process wire/argument contract does not actually carry.

## 4. Conformance and Closure

**Date:** 2026-09-28

The final closure stage is defined as cross-language behavioral verification.

Required conformance cases:

1. mono input to stereo output;
2. stereo input to stereo output;
3. multiple synchronized offsets;
4. per-input gain;
5. master gain;
6. left/right gain;
7. pan;
8. clipping and saturation;
9. malformed WAV;
10. truncated WAV chunks;
11. sample-rate mismatch;
12. zero/invalid configuration;
13. one-input boundary;
14. 128-input boundary;
15. output-size overflow protection;
16. C/C++ equivalent PCM output for identical fixtures.

### EQ status

The public C, C++, and Java models expose:

- bass;
- mid;
- treble.

The current native mixer does **not** yet implement those EQ controls.

Accordingly, EQ is recorded as an explicit closure item rather than silently treated as complete.

The implementation order for the final Audio API is therefore:

**1. Native foundation → 2. Language and GUI boundary → 3. Contract definition → 4. Cross-language conformance and capability closure.**
