SLGovPhase #sleela 2.5 (lib/opcodes/governance/SLGovPhase.sleela)

SLGovPhase class

Defines SLGovPhase, the shared phase vocabulary that lets SLeeLa and the VM know when to listen for ordering around opcode execution. A governed opcode stream is observed at three moments the user named: BEFORE — the Registrar considers the whole program A -> B before any opcode runs, and admits, rejects, or pauses it. DURING — the Listener watches the live VM code as each opcode arrives and confirms the admitted sequence still fits the program as it comes. AFTER — the EventObserver judges the completed operation(s) against the architectural and ethical base concepts and may warn or patch. Both SLeeLa (source side) and the VM (runtime side) register their interest in these phases; the orchestrator (SLGovernedExecution) fires them in order. Family: opcodes.governance. SLGovVerdict #sleela 2.5 (lib/opcodes/governance/SLGovVerdict.sleela)

SLGovVerdict class

Defines SLGovVerdict, the discretionary outcome a governance principal (Registrar, Listener, EventObserver) returns about an opcode or an opcode sequence. This is the "discretion in SLeeLa herself" the user asked for: rather than a raw boolean pass/fail, a verdict carries a graded disposition so the program can be admitted, warned about, patched, paused as unrest, or rejected. Dispositions, from most permissive to most restrictive: ADMIT — the opcode/sequence is in order; proceed. WARN — proceed, but a concern was recorded (non-blocking). PATCH — a known, safe correction was applied via a symbol map; proceed with the patched form. PAUSE — hold the program as "unrest": not rejected, but it may not run until a human or a higher authority resolves the concern. REJECT — the opcode/sequence is out of order unto itself; refuse it. Family: opcodes.governance. Native VM/OS work crosses an explicit bridge.
