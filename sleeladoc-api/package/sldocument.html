SLDocument #sleela 2.5 (lib/sldocument/SLDocument.sleela)

SLDocument class

Defines SLDocument, an ordered .sldocument whose annotated method steps run top-down and are compiled against and with standard SLeeLa source. An .sldocument is a document, not a free script: its order is already established, so running it is a matter of flow and architecture rather than control plumbing. These documents suit tasks more sophisticated than bash scripting, and clear "national program" work where the sequence A..Z is settled in advance. Running the document: 1. steps are arranged by effective order (explicit @order, else top-down); 2. each step is invoked in that order and its single binary veritable value is recorded; 3. by default the document stops at the first unsound step (fail-closed), because an ordered program should not proceed past a broken step; this may be relaxed with permitContinue() to record every step. Family: sldocument. Native VM/OS work crosses an explicit bridge.

SLDocumentAnnotation #sleela 2.5 (lib/sldocument/SLDocumentAnnotation.sleela)

SLDocumentAnnotation class

Defines SLDocumentAnnotation, the annotation vocabulary that marks how an .sldocument step is named and ordered. A step's method may be annotated to indicate its order, its function, or it may simply be named as the method itself. The three annotation kinds: ORDER — @order(n): an explicit 1-based position in the top-down run. FUNCTION — @function("name"): the step's declared role/purpose, independent of its identifier. METHOD — no annotation: the method name itself is the step's name, and its order is its textual position in the document (top-down). When ORDER is present it governs; otherwise textual order governs. A FUNCTION annotation never changes order, only the step's declared purpose. Family: sldocument. Native VM/OS work crosses an explicit bridge.

SLDocumentCompiler #sleela 2.5 (lib/sldocument/SLDocumentCompiler.sleela)

SLDocumentCompiler class

Defines SLDocumentCompiler, which compiles an .sldocument against and with standard SLeeLa source so the document's ordered steps resolve to compiled methods on the same VM. An .sldocument is not interpreted in isolation: its step methods are ordinary SLeeLa, compiled through the normal SLeeLa Compiler path alongside the accompanying .sleela source units. This class is the document-aware front end to that path. It: 1. registers the companion .sleela source so symbols the steps call resolve; 2. lowers each annotated step to a method entry the VM can invoke; 3. validates that the resolved order has no gaps or duplicate @order values; 4. yields a frame handle the SLDocument runs against. The authoritative compilation remains the SLeeLa Compiler (lib/compiler / impl/frontend); this class drives it with document semantics. Family: sldocument. Native VM/OS work crosses an explicit bridge.

SLSourceNameComparison class

Defines SLSourceNameComparison, which compares the naming of a .sleela program against a .sldocument so an engineer can see how the two forms line up before or after a conversion. The two forms name things differently: - .sleela names every method explicitly (it is class/method shaped); - .sldocument may leave steps anonymous (ordered position or role only). This comparison pairs each document step with the .sleela method name it would have (via SLDocumentNaming) and reports, per step, whether the names match, whether a name had to be synthesized, and whether any collision arose. SLVeritable #sleela 2.5 (lib/sldocument/SLVeritable.sleela)

SLVeritable class

Defines SLVeritable, the single binary value an .sldocument step usually returns — a verified truth that is "veritable and kind". An .sldocument runs top-down, and each ordered step generally returns one binary item. That item is modeled here as a two-fold judgement: - veritable: the step's result is true / holds (the binary truth), AND - kind: the result is well-formed and benign — the right *kind* of value, not a malformed or hostile one. Both must hold for the value to be "sound". A step that produces a true but ill-formed result is veritable-but-not-kind, and the document does not treat it as a clean pass. Family: sldocument. Native VM/OS work crosses an explicit bridge.
