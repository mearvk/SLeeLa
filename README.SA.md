# SLeeLa 3.0 — المملكة العربية السعودية (SA)

## العربية

SLeeLa لغة برمجة أنظمة أصلية تضم مُصرّفًا وبيئة تشغيل ومنظومة آلات افتراضية. تتكامل اللغة والمُصرّف والمكتبات وأدوات التطوير وعقود المنصات لبناء البرمجيات وتشغيلها.

**The Now. The Ingredient.** لا تقتصر لغة البرمجة على قواعدها النحوية؛ فالمُصرّف وبيئة التشغيل والمكتبات والأدوات تشكّل معًا نظامًا برمجيًا قابلًا للاستخدام.

## II. البناء والاختبار

تشمل المتطلبات سلسلة أدوات C/C++ مثل GCC أو Clang، وGNU Make، وPython 3. وقد تحتاج المكونات الرسومية على Linux إلى حزم التطوير الخاصة بـ X11/Xrandr.

نفّذ الأوامر التالية من المجلد الرئيسي للمستودع:

```sh
make
make -C impl all
bash ./test-suites/run-all.sh --all
```

نجاح بناء مكوّن واحد لا يعني أن جميع المكتبات أو المنصات جاهزة للإصدار. راجع وثائق البناء والمنصات لمعرفة متطلبات كل هدف.

## III. التثبيت

```sh
sudo make install
make install PREFIX="$HOME/.local"
make install DESTDIR="$PWD/package-root"
make install-check
```

بادئة التثبيت على مستوى النظام هي عادةً `/usr/local`. يتيح استخدام `PREFIX="$HOME/.local"` التثبيت ضمن مساحة المستخدم، ولا يتطلب عادةً صلاحيات المسؤول. راجع [دليل التثبيت](install/README.md) لمعرفة الخيارات والتفاصيل.

## IV. اللغة وبيئة التشغيل

تُعرّف القواعد النحوية المعتمدة في [`SLEELA.syntax`](SLEELA.syntax). تعتمد وثائق المستودع صياغة اللغة **3.0**. إصدار المُصرّف وإصدار صياغة لغة المصدر مفهومان مختلفان.

تشمل المراجع التقنية حقول `@mix` المتجاورة، وعائلات الأعداد الصحيحة الموسعة، وعلامات مستندات Preonem، وSleelaDoc، وتوليد وثائق API، وأدوات Nordshrift. تبقى المعرّفات التقنية والأوامر وأسماء الملفات وواجهات API وأمثلة الشيفرة دون تغيير لتظل قابلة للاستخدام مباشرةً.

## V. مبادئ الهندسة والتحقق

تعطي SLeeLa الأولوية للأدلة، والعقود الواضحة بين المكونات، وقابلية النقل، والسلوك الآمن عند الإخفاق، والإصدارات القابلة لإعادة الإنتاج. يجب تقييم حالة التحقق لكل وحدة ومنصة على حدة. لا يجوز الإبلاغ عن الاختبارات التي تم تجاوزها على أنها ناجحة، كما أن نجاح بناء مكوّن واحد لا يُعد تحققًا كاملًا من الإصدار.

تتضمن أدوات الحماية Sleelavirin مدقق SHA-256 محليًا، وموائم ClamAV اختياريًا، وبيان سلامة الملفات. لا يُعد الإصدار متحققًا منه إلا بعد اكتمال فحوص CI الخاصة بالتزام الإصدار ومراجعة الملفات الناتجة.

## VIII. معمارية المترجم ومسار الترجمة

يفصل SLeeLa بين لغة المصدر وواجهة المترجم والتمثيل الوسيط وتوليد الشيفرة وبيئة التشغيل. إصدار المترجم وإصدار الصياغة وإصدار VM/ISA مسارات مستقلة. وجود ميزة في المواصفة لا يثبت أنها منفذة ومتحقق منها على كل هدف.

يتكون المسار المعتاد من ملفات `.sleela`، والتحليل المعجمي والنحوي، والتحليل الدلالي، والتمثيل الوسيط، وتوليد المخرجات للأهداف المدعومة، ثم التنفيذ في runtime. المرجع المعياري هو [SLEELA.syntax](SLEELA.syntax)، وتوضح [وثيقة اللغة الدولية](LANGUAGE.INTERNATIONAL.3.0.md) تفاصيل الأنواع والكائنات والتوافق.

## IX. الأنواع ونموذج الكائنات

تشمل الأنواع الأساسية `int` و`double` و`boolean` و`String` و`void` وأنواع `struct` المعلنة وتواقيع reference types المدعومة. وفق التوثيق الحالي، فإن `int` و`long` و`int64` أعداد صحيحة موقعة بعرض 64 بت. يقبل `int128` كنوع صحيح، لكن التنفيذ الحالي يستند إلى 64 بت ولا ينبغي اعتباره حساباً كاملاً بعرض 128 بت.

إن `struct` بنية مجمعة ذات حقول مسماة. مقابض struct التي يديرها VM ليست مؤشرات خاماً مكشوفة. تشارك عمليات الإسناد وتمرير المعاملات النسخة نفسها، وتستند المساواة إلى الهوية. لنقل البيانات بصورة قابلة للتشغيل البيني استخدم وسائل التسلسل الموثقة مثل `structPack(instance)` و`structUnpack(TypeName, json)`؛ فمقبض VM المحلي ليس قيمة شبكة قابلة للنقل.

تحتوي الفئات على fields وmethods. في نموذج التنفيذ الحالي تمثل fields حالة مشتركة للفئة، بينما تكون المتغيرات المحلية للطريقة خاصة بكل thread. تخضع الوراثة والفئات المتداخلة وgenerics لإصدارات syntax محددة. راجع [International Language Reference](LANGUAGE.INTERNATIONAL.3.0.md).

## X. تدفق التحكم وتوقيت الحلقات

تدعم اللغة الشروط والحلقات واستدعاء methods والعودية. تحدد التعليمتان `@loopDelay` و`@loopBudget` فترة توقف أو ميزانية زمنية للحلقة، وتكتبان قبل الحلقة وتتحولان إلى تعليمة VM المسماة `OP_SLEEP` (ISA 157). كما تستخدم الدالة المضمنة `sleep(ms)` التعليمة نفسها.

```sleela
@loopDelay(ms = 250)
while (running) {
    processNext();
}
```

يعرض المثال شكل الصياغة فقط؛ ويجب تعريف identifiers والفئة المحيطة في البرنامج الفعلي. راجع [SLEELA.syntax §32](SLEELA.syntax) و[Loop Timing API](api/sleela/3.0/LOOP_TIMING_API.md).

## XI. المكتبات والوحدات الرئيسية

يضم المستودع وحدات ذات مستويات نضج مختلفة:

- `lib/advantage` — تقييم متعدد الطبقات لنتيجة مقارنة بنموذج، ويشمل الرياضيات واقتصاديات التجارة الثنائية والتكامل والتقييم والمخرجات الموجهة. وصف حقول الثقة المستوحى من الفيزياء هو تشبيه نمذجة وليس ادعاءً بقانون فيزيائي.
- `lib/xml` — شجرة مستند XML بعقد element وtext وcomment وCDATA وprocessing instruction، مع attributes وparser وserializer.
- `lib/text` — عمليات النص والسلاسل القائمة على خلايا المحارف، مثل `charAt` و`substring` و`indexOf` و`reverse` والتنسيق الموضعي.
- `lib/sleeladoc` — استخراج توثيق المصدر وصفحات مرجعية عبر CLI. تعرض `sleela docs` الموضوعات والحزم والفئات؛ وتنشئ `sleela docs --generate [dir]` مجموعة نصية محلية للعمل دون اتصال.
- `lib/cpu` و`lib/xlt` — ملفات تعريف CPU ومكونات البنية وصيغة النماذج ومراجع التوقيت.
- `recursion/stanchion` — نماذج مرجعية وأمثلة C/C++ للعودية.

وجود الوحدة في الفهرس لا يعني أنها جاهزة للإنتاج. راجع README الخاص بها وتغطية الاختبارات وحدود المنصات وسجل التحقق.

## XII. تكامل C/C++ وحدود native

يتضمن المستودع مكونات C وC++ ومساراً محدوداً لتوليد الشيفرة native. ترتبط العلامة `@native` والأمر `sleela aot` بتطوير native، ولا يمثلان تصريحاً عاماً بتشغيل أي شيفرة native.

يجب أن يحدد تكامل C/C++ بوضوح ABI واتفاقية الاستدعاء وملكية الذاكرة وتخطيط البيانات ومعالجة الأخطاء واعتماديات المنصة. تعامل مع الشيفرة native بوصفها حد ثقة مستقلاً. المرجع يحدد المورد ولا يمنح إذناً بالتنفيذ. راجع [native implementation](impl/README.md) و[platform matrix](docs/PLATFORM-SUPPORT.md) و[comparison standards](comparison/README.md).

## XIII. البناء والتثبيت ودعم المنصات

يتطلب البناء native عادةً toolchain للـ C/C++ مثل GCC أو Clang وGNU Make. تستخدم بعض الأدوات Python 3، وقد تحتاج مكونات GUI في Linux إلى حزم تطوير X11 وXRandR.

```sh
make
make -C impl all
bash ./test-suites/run-all.sh --all
```

للتثبيت على مستوى النظام:

```sh
sudo make install
```

وللتثبيت للمستخدم الحالي فقط:

```sh
make install PREFIX="$HOME/.local"
```

راجع [دليل التثبيت](install/README.md) و[مصفوفة دعم المنصات](docs/PLATFORM-SUPPORT.md). لا تفترض تطابق المتطلبات والأوامر بين Linux وmacOS وWindows.

## XIV. الأمان والسلامة والاختبارات

يمكن لملفات hash manifests وأدوات التحقق مقارنة الملفات بالمحتوى المتوقع. تنطبق نتيجة PASS فقط على النطاق والوقت المحددين للفحص. يجب أن تميز تقارير الاختبار بين pass وfail وskip؛ ولا يجوز وصف الاختبارات المتروكة أو غير المشغلة بأنها ناجحة.

المبادئ الأساسية:

- تحدد references الموارد ولا تمنح إذناً بالتنفيذ.
- يجب أن تكون واجهات native صريحة ومحدودة.
- يجب دعم ادعاءات المنصات ببناء واختبارات فعلية.
- يجب تتبع الوثائق المولدة إلى المصدر وgenerator.
- عند غياب بيانات integrity الضرورية، ينبغي أن تفشل فحوص الأمان بطريقة آمنة.

راجع [سياسة الاختبار](markdown/TESTING.md) و[التحقق من المنصات](docs/PLATFORM-SUPPORT.md).

## XVIII. عقود واجهات الوحدات واستراتيجية الاختبار

عند إضافة API جديد، وثّق المدخلات والمخرجات وشروط الخطأ وملكية البيانات وما إذا كانت العملية تُحدث side effects. ينبغي أن تعرض الأمثلة الاستخدام المعتاد والتعامل مع invalid أو missing input. لا تصف سلوكاً بأنه مضمون ما لم تؤكده implementation والاختبارات ذات الصلة.

قسّم الاختبارات وفق مراحل compiler pipeline: lexing/parsing وsemantic analysis وIR lowering وcode generation وVM execution وnative integration. احتفظ لكل regression case بأصغر مدخل قابل لإعادة الإنتاج، والنتيجة المتوقعة، والنتيجة الفعلية. يجب أن تشرح تغييرات API مدى backward compatibility وخطوات migration وتأثيرها في examples الحالية.
